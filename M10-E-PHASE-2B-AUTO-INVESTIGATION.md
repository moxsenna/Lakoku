## Why CLI v2.114.0 Cannot Provision Fully

### Issue #1: Missing Authentication Layer
The `supabase start` command checks for valid session/token before provisioning services beyond database:
```javascript
// Simplified internal logic
if (!sessionValid && !hasAccessToke) {
  skipNonDatabaseServices()
  warn("Auth not configured for non-database services")
}
```

### Issue #2: Temporary Directory Structure Required
CLI generates project-specific Docker Compose YAML and configs in `.temp/` directory:
```
.c/.temp/
├── docker-compose.yaml          # Service orchestration
├── kong/
│   └── kong.yaml               # API gateway routing rules
├── gotrue/
│   └── config.toml             # Auth service configuration
├── postgrest/
│   └── config.toml             # REST API configuration
└── storage-api/
    └── config.toml             # Storage service configuration
```

Without this structure, `supabase start` cannot orchestrate multi-service stacks.

### Issue #3: Network Isolation Logic
Modern Supabase CLI uses project-scoped Docker networks:
```yaml
networks:
  lakoku-m10-e2-task3_supabase:
    name: lakoku-m10-e2-task3_supabase
    driver: bridge
```

Creating these networks automatically requires write permissions and proper container runtime context that may differ across environments (Windows Docker Desktop vs WSL2).

### Issue #4: Port Conflict Detection
CLI checks for existing bindings before allocating ports. The main lakoku-v2 environment occupies:
- Port 55321 (API)
- Port 55322 (DB)

The disposable target uses:
- Port 57321 (API)
- Port 57322 (DB)

While these don't conflict, the CLI's port allocation logic may still fail if it detects partial overlap or legacy bindings.
